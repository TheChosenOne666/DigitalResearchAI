## 二、需求 1：智搜任务管控与断点续跑

### 2.1 痛点

1. **生成中断即全丢**：报告生成过程只在前端累积展示，中途失败、关页面、断网后已生成的内容不保留，用户要重新走「选数据 → 生成」，此前的勾选偏好一并丢失。
2. **没有任务视图**：用户不知道自己发起过哪些检索/生成、现在处于什么状态。除历史记录里已完成的报告外，在途任务关闭页面后就无从找回。
3. **中止不可续**：现有「停止」按钮只能终止，终止后无任何后续动作入口，等于白等。
4. **无法并行推进多件事**：用户发问 A 后想先处理 B，只能等 A 结束或强行中止 A。

### 2.2 使用场景

**场景 1：生成中断后续跑**
用户对「2026 秋招计算机 28 届实习转正」发起生成，跑到一半网络抖动。用户回来打开智搜页，任务列表里该任务显示「生成中断（已生成 62%）」，点「继续生成」→ 从断点接着写 → 补成一份完整报告。全程不重新检索、不重复扣费。

**场景 2：多任务并行**
用户同时关心三个问题，连续发起三次检索。任务列表里三条任务各自显示状态（检索中 / 待选择 / 生成中），用户可分别中止其中一条，也可对已完成检索的那条先进入选数据。

**场景 3：任务完成后回访**
用户今天发起、明天回来，任务列表仍能看到昨天已完成的任务，点一下直接打开对应报告。

**场景 4：失败重试**
检索阶段失败（外部源超时全灭）→ 任务显示「检索失败」→ 点「重试」→ 重新检索。
生成阶段失败 → 任务显示「生成失败（断点已保留）」→ 点「继续生成」→ 从断点续跑。

### 2.3 验收标准

> 完成情况（2026-09-10）：任务列表、持久化、断点续跑、中止/删除、越权隔离均已落地并端到端验证。**三处偏差**：
> ① 状态机去掉「排队中」，**任务并发上限与排队自动推进不做**——真排队需把检索/生成改造成后台作业（BullMQ），与「SSE 直连」模型冲突；并发压力由既有 SSE 槽位限流（M7.2，超限 429）承担；
> ② **不提供独立的「重试」接口**：检索失败时试额已回滚，前端用原问题重新发起检索即可（净效果等价于「不重复扣费」）；
> ③ 僵尸任务在**服务启动时**收敛（不引入定时任务）。

**任务列表**

- [x] 智搜页提供任务列表入口（右下角「任务」浮动按钮 → 任务中心抽屉），展示任务类型（检索 / 生成）、问题摘要、状态、发起时间、进度
- [x] 任务状态机：检索中 / 待选择 / 生成中 / 已完成 / 检索失败 / 生成中断 / 已中止（「排队中」见偏差①）
- [x] 列表按发起时间倒序，支持按状态筛选（进行中 / 已完成 / 失败）

**持久化与恢复**

- [x] 刷新页面、关闭浏览器、重新登录后任务列表与状态仍可恢复（服务端 `search_tasks` 表持久化）
- [x] 在途任务在服务端重启后被收敛为「生成中断」（可续跑），不会永远卡在进行中

**断点续跑**

- [x] 生成中断后任务进入可续跑态（生成中断 / 已中止），且**已生成章节内容被保留**（草稿 + 章节落库）
- [x] 点「继续生成」从断点续跑，最终产出完整报告；不重新检索、不重复扣费（计费仍在检索段）
- [x] 续跑产出**不出现重复段落**：实测续跑后三个章节标题各出现 1 次（分段生成 + 章节级断点的直接结果）
- [x] 续跑可多次进行：再次中断后断点继续保留
- [x] 续跑报告与一次性生成结构一致（章节完整、引文角标与来源卡联动正常）

**续跑窗口（2026-09-10 补充）**

续跑复用检索快照（不重新检索、不重复扣费），因此受快照有效期约束，需让用户提前知情：

- [x] 续跑窗口 = 检索快照有效期（30 分钟），与快照恢复窗口同源同值
- [x] 任务列表展示剩余可续跑时间（「可在 N 分钟内继续生成」）
- [x] 窗口过期后**不再提供「继续生成」**（避免必然失败的点击），转为「重新检索」按钮，点击用原问题重新走检索流程
- [x] 窗口过期时服务端**真实拒绝**续跑：返回 HTTP 400（业务码 3001），提示「检索结果已过期（超过 30 分钟），请重新勾选并点击开始分析」——不再静默使用过期快照
- [x] 点历史记录中的「待选择」会话**直接回到首页智搜并加载该会话**（问题 / 来源 / 勾选全部回填），过期与否都照常展示内容（2026-09-13 补充）
- [x] 过期会话在选择态提示条上明示：转警示色 + 「检索结果已过期，需重新检索后才能分析」，主按钮变「重新检索」，点击用原问题重跑检索；未过期则为常规「开始分析」
- [x] 窗口过期不改变任务状态（仍为「生成中断 / 已中止」），历史断点内容保留
- [x] 过期快照**物理回收**：每次新检索顺手清理本租户已过期快照（懒删除，不引入定时任务），避免行内来源正文长期堆积

> 说明（含更正）：批 4 复核时发现 TTL 三处不一致——快照恢复接口与**生成入口**均已强制校验，**只有续跑路径漏了**（仅校验快照是否存在）；同时过期快照完全没有回收机制。本轮把续跑校验补齐、并新增强制「窗口可见 + 过期引导」，连同懒删除一并落地。此前记录曾笼统写作"窗口从未生效"，属表述过头，已更正。

**中止 / 重试 / 删除**

- [x] 进行中的任务可中止；中止后状态为「已中止」，保留断点内容并可续跑（前端「停止」与任务列表「中止」两条路径）
- [x] 检索失败的任务可重试（前端用原问题重新发起检索，失败时试额已回滚，不重复扣费；见偏差②）
- [x] 已完成任务可从列表打开对应报告（「查看报告」跳报告详情页）
- [x] 任务可删除；删除任务记录**不连带删除报告**（实测删除后报告详情仍可访问）

**并发与边界**

- [~] 任务并发上限 + 排队自动推进：**本轮不做**（见偏差①），并发压力由既有 SSE 槽位限流承担
- [x] 越权访问：他人任务在列表中不可见，操作他人任务返回 404（跨用户 / 跨租户均不可见、不可操作）
- [x] 任务列表为空时展示空态提示，不报错

## 四、需求 3：智搜补充上传本地资料

### 4.1 痛点

1. **死入口**：智搜输入框左侧的「+」当前点击只弹一句"将在数据源接入中提供"，是明确的未实现占位。
2. **手头资料用不上**：用户手上常有本地研究资料（Excel 数据表、研报 PDF、Word 文档），其权威性未必低于检索回来的外网内容，但当前完全没有入口让这些资料进入报告。
3. **客户需求未落地**：客户「数据上传」功能点列明 Excel、CSV 上传（数据库连接 / API 导入此前已按原型裁剪）。

### 4.2 使用场景

**场景 1：本地资料 + 检索结果合并分析**
用户上传 1 个 Excel（自有统计数据）+ 1 个 PDF（行业研报），再提问题。系统把两个文件解析为「本地资料」来源，与检索结果并列展示在选数据态；用户勾选全部 → 一并参与报告生成，可被 `{c:N}` 引用。

**场景 2：只用自传资料**
用户不信任外网数据，上传资料后把检索来源全部取消勾选，只保留自传资料 → 报告完全基于本地资料。

**场景 3：上传异常**
用户上传一个 .zip / 超 20MB 的文件 → 明确提示「格式不支持，支持 xlsx/xls/csv/docx/doc/pdf/txt/md」或「文件超过 20MB」，且不影响本次检索正常进行。

### 4.3 验收标准

> 完成情况（2026-09-10）：上传解析、并入来源、置顶与连续编号、仅凭上传资料生成均已落地并端到端验证。**两处偏差**：
> ① 拖拽上传已实现并**于同日完成自动化实测**（浏览器派发 drop 事件，chip 正确显示中文名）；
> ② 「任务删除时清理」已接线（`SearchTaskService.remove` → `cleanupExpired`），但**语义为按用户清理已过期资料**而非按任务精确清理——`search_uploads` 与会话/任务无关联字段（上传发生在检索之前），精确关联需另加字段。

**上传入口与限制**

- [x] 智搜输入框「+」可打开文件选择，支持拖拽（**拖拽已自动化实测通过**：派发 drop 事件后 chip 正确显示中文名）

## 五、需求 4：知识库优先匹配（串行兜底）

### 5.1 痛点

客户需求原文是「查询优先调取知识库，无匹配再外网检索」。当前实现是三路**并行** + 本地路加权 ×1.2，外网结果即使知识库已有权威答案也会一并混入报告 —— 与「知识库优先」的产品定位不符，也浪费外部检索成本。

### 5.2 使用场景

**场景 1：知识库命中足够 → 不联网**
用户提问，知识库中有足够命中 → 报告完全基于知识库结果生成，不发起外网检索。用户可见提示「已命中知识库，未联网检索」（更快、结果更可控）。

**场景 2：知识库命中不足 → 补联网**
知识库只有零星命中，达不到"足够"标准 → 自动继续外网检索，结果合并后进入选择态。

**场景 3：显式模式不受影响**
用户把模式切到「联网」→ 只走外网；切到「知识库」→ 只走知识库，都不触发兜底逻辑。

### 5.3 验收标准

> 完成情况（2026-09-10）：短路判定、可见性、兼容回归均已落地并验证。**两处偏差**：
> ① 阈值走环境变量（`KB_FIRST_MIN_HITS`/`KB_FIRST_MIN_SCORE`，改动需重启），未接管理端「系统参数」；
> ② 实际路由记录在 **SSE `search_route` 事件 + 服务端日志**，未落入检索快照（避免为此加表字段/migration），排查诉求已满足，如需落库另开。

**短路判定**

- [x] 混合模式下：先执行知识库检索，判定命中是否「足够」
- [x] 判定足够 → **不发起外网检索请求**，直接用知识库结果进入选数据态
- [x] 判定不足 → 继续执行外网检索，两路结果合并（沿用现有融合排序）
- [x] 「足够」的判定规则明确且可配置：命中条数 ≥ 阈值（默认 3 条）且最高相似度 ≥ 阈值（默认 0.5）
- [x] 阈值可配置（环境变量；非管理端系统参数，见上方偏差①）

**用户可见性与排查**

- [x] 短路发生时，前端在检索阶段给出明确提示（「已命中知识库（N 条，最高相似度 X%），未联网检索」），让用户知道结果来源
- [x] 实际检索路与是否短路可事后排查（SSE 事件 + 日志，见上方偏差②）
- [x] 日志中记录短路判定的依据（命中条数、最高相似度）

**兼容与回归**

- [x] 「联网」模式：行为与现状完全一致（仍走联网 + 垂直）
- [x] 「知识库」模式：只走知识库，不因兜底逻辑而发起外网请求
- [x] 知识库为空 / 本地路失败 → 视为"不足"，正常兜底外网，不报错
- [x] 计费语义不变：检索段仍扣 1 次配额（短路时同样扣）
- [ ] 未勾选/过期等既有校验逻辑不受影响

**性能**

- [x] 短路路径不发起外网请求（实测 `routes` 仅 `local`），省去联网 + 垂直两路耗时
- [ ] 兜底路径（知识库不足 → 补外网）总耗时实测 —— **待补**：本机知识库无数据，本轮仅验证了兜底行为正确，未做耗时对比
