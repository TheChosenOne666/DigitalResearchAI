## 二、M7.1 可观测四件套

### 2.1 Pino 结构化日志 + requestId 贯穿

**新增依赖**：`nestjs-pino`、`pino`、`pino-http`（dev：`pino-pretty`）。

**设计**：
- `LoggerModule.forRoot` 替换 Nest 默认 Logger；`pino-http` 的 `genReqId` 从请求头 `X-Request-Id` 取（保留网关/上游传入），否则生成 `req-<8位随机>-<毫秒>`，并回写响应头
- **AsyncLocalStorage 请求上下文**（`common/observability/request-context.ts`）：中间件把 requestId + 用户信息存入 ALS，供拦截器、异常过滤器、业务 Service 在任意深度取用；非 HTTP 上下文（BullMQ worker）提供 `runWithRequestId(jobId, fn)` 包裹，worker 日志同样带出 requestId
- 输出：dev 走 pino-pretty（`LOG_PRETTY=true`），默认 JSON 单行；`redact` 屏蔽 authorization/cookie/密码字段
- `AllExceptionsFilter` / `TransformInterceptor` 改用注入的 PinoLogger，日志行统一携带 requestId

### 2.2 Prometheus 指标 + 告警四项

**新增依赖**：`prom-client`。新增 `common/observability/metrics.*`：

| 指标 | 类型 | 标签 | 用途（验收告警项） |
| --- | --- | --- | --- |
| `http_request_duration_seconds` | Histogram | method、route、status | P95/P99 时延 |
| `sse_active_connections` | Gauge | — | SSE 并发数 |
| `sse_connections_total` / `sse_disconnects_total` | Counter | — | SSE 断连率（两者差分） |
| `queue_job_counts` | Gauge | queue、state | BullMQ 队列积压（waiting>阈值告警） |
| `llm_calls_total` | Counter | scene、status | LLM 错误率（error/total 比率） |

- 埋点位置：`MetricsInterceptor`（HTTP 时延，route 取 Controller 路径模板避免高基数）；`search.controller` SSE 流开始/关闭处（SSE 三指标）；`generate.service` / `intent.service` streamText/generateObject 成功失败处（llm_calls_total）；metrics service 内 15s 轮询 `chunk-embed` 队列 `getJobCounts()`（queue_job_counts）
- 暴露：`GET /api/v1/metrics`，`@Public()` + 绕过 TransformInterceptor 原样输出 `text/plain`（生产由 Nginx 限内网访问）
- 告警规则：`infra/prometheus/alerts.yml` 落四条（P95>5s、SSE 断连率>10%、队列 waiting>100、LLM 错误率>20% 5min 窗口），Prometheus 加载

### 2.3 OTel 管道 span

**新增依赖**：`@opentelemetry/api`、`@opentelemetry/sdk-node`、`@opentelemetry/exporter-trace-otlp-http`、`@opentelemetry/resources`、`@opentelemetry/semantic-conventions`。

- `common/observability/otel.ts`：`NodeSDK` 手动初始化，OTLP HTTP 导出到 `OTEL_EXPORTER_OTLP_ENDPOINT`（默认 `http://localhost:4318/v1/traces`）；`OTEL_ENABLED!=='true'` 时整链不启动（api 包 trace.getTracer 退化为 no-op，零开销）

- docker-compose 加 `jaegertracing/all-in-one`（16686 UI / 4318 OTLP）

## 八、阶段记录

### M7.2 压测实测（2026-09-07）

**环境**：本地 PG（ai-postgres）+ Redis（ai-redis）+ dev 服务；LLM 火山方舟 deepseek-v4-pro-ga-260813。
**限流阈值（sys_configs 实测）**：`rate.globalRate=1000`、`rate.globalBurst=10000`、`rate.sseMaxConcurrent=50`（auth 组未配置，用默认 0.5/s + burst 30）。

**工作台接口压测**（`bench-workspace.mjs`，并发 20 / 200 请求，命中 global 桶）：
- 成功率 100%、吞吐 314.5 req/s、延迟 P50=58ms / P95=117ms / P99=181ms、无 429。
- global 桶 rate=1000/s + burst=10000，200 请求远未触顶，符合预期。

**SSE 搜索链路压测**（`bench-sse.mjs`）：
- 单路全流程 73.4s（首包 14ms），瓶颈在 LLM 生成，非建连/检索/融合。
- 并发 10 / 20 路、timeout=150s：成功率 100%、断连 0、首包 P50=41ms / P95=81ms、总耗时 P50=51.8s / P95=80.4s / P99=88.0s。
- 并发 10 未触发 SSE 并发限流（sseMaxConcurrent=50）。

**单路阶段耗时拆解**（两次实测）：intent 意图分类 5.0s（命中 5s 超时熔断）→ searching 检索+rerank 7.1s / 11ms（rerank 3s 超时熔断；二次命中缓存后仅 11ms）→ fusing 融合 0ms → generating 生成 64~108s。**生成阶段中 TTFT（首 token 延迟）高达 59~103s，且二次反而更慢（排除冷启动），流式输出仅 4.4~4.8s**——即报告篇幅不长、生成吞吐正常，慢在 deepseek-v4-pro-ga-260813 的首字延迟。

**发现与调整**：
1. `bench-sse.mjs` 原默认 timeout=60s 小于实测单路 73s，默认参数必现假性超时（首轮 30 路出现 76.7% 超时即此因）。已上调默认 timeout 为 120s。
2. 核心性能瓶颈 = LLM 首 token 延迟（TTFT 59~103s，方舟 deepseek-v4-pro-ga-260813），非检索/融合/流式吞吐。优化方向：换首字更快的模型、或对推理型模型单独评估；意图分类/rerank 当前 5s/3s 超时熔断降级，换快模型后可恢复质量。
3. `/metrics` 端点正常（挂载于 `/api/v1/metrics`，返回 Prometheus 指标），M7.1 可观测性已生效。

**TTFT 根因定位（方舟模型实测，2026-09-07）**：
- 同一 deepseek-v4-pro-ga 在**简短 prompt 下 TTFT 仅 9.4~12.7s**，而真实智搜（带 ≤6 条 × 2000 字符参考资料的长 prompt）暴涨到 59~103s → 根因是「推理型模型 + 长参考资料 prompt」：模型输出前做思考推理，输入越长思考越久，非冷启动/网络。
- 方舟账号（2113824813）实际仅开通 2 个可用 LLM 文本模型：`deepseek-v4-pro-ga-260813`（TTFT 9~13s）、`glm-5-2-260617`（TTFT 11~14s，同为推理型）。其余快版（`deepseek-v4-flash-ga-260731`、`doubao-seed-2-1-turbo`、`glm-4-5-air`、`qwen3-*`）均返回 `ModelNotOpen`/`NotFound`，需在方舟控制台开通。
- 可选优化（待拍板）：① 方舟控制台开通 `deepseek-v4-flash-ga`（同系列快版，改 `LLM_MODEL` 即可）；② 代码侧缩减参考资料（`SOURCE_CONTENT_LIMIT` 2000↓、引用条数 6↓），直接压低长 prompt 推理时间；③ 前端展示推理进度（若支持 reasoning_content 流式）。

**metrics 交叉验证 + 配置缺陷（2026-09-07）**：
- `/api/v1/metrics` 显示 `llm_calls_total{scene="intent",status="error"}=56`、`{scene="rerank",status="error"}=13`、`{scene="report",status="ok"}=56`——即意图分类与 rerank 的 LLM 调用 **100% error**。
- 根因：intent/rerank 超时阈值（5s/3s）短于 deepseek-v4-pro 实际 TTFT（9~13s），导致这两环节**永远超时熔断降级、从未真正工作**，属配置错误而非性能问题。修复需调高超时阈值（代价：该两环节延迟上升）或换更快的意图/rerank 模型。

**渗透测试复测（2026-09-07）**：`security-audit.mjs` 实测 **PASS 16 / FAIL 0 / WARN 0 / SKIP 0**（未授权扫描 8 项、租户越权 2 项、注入探测 4 项、支付重放 1 项、限流绕过 1 项），与 M7.3 首次验收结果一致，无回归。

**报告模板化改造 + 压测对比（2026-09-08）**：
- 背景：TTFT 慢的根因是「推理型模型 × 长参考资料」。用户拍板采用「固定报告模板」方案（不关思考、不换模型）。
- 改造：`GenerateService.GENERATE_SYSTEM` 由笼统要求改为固定三章模板——核心结论（1-2 句）/ 关键数据（3-5 条）/ 分析解读（2-3 点），约束输出结构与篇幅；`{c:N}` 引文机制与安全规则不变。
- 单路实测（充值后）：TTFT **35.2s**（改造前 59~103s）、全流程 **40.6s**（改造前 73.4s）、报告正文 **655 字**（模板约束篇幅）。
- 并发 10 / 20 路、timeout=150s：成功率 100%、断连 0、完整五阶段 100%、首包 P50=41ms / P95=107ms、总耗时 **P50=35.4s / P95=55.5s / P99=63.9s**。
- 对比改造前（P50=51.8s / P95=80.4s / P99=88.0s）：总耗时下降约 **27%~32%**，报告篇幅从长报告缩至 655 字，模板三章标题 100% 命中。
- 结论：固定模板通过「约束输出长度 + 固定结构减少自由发挥」使总耗时全面下降，是「不换模型 / 不关思考」前提下的有效提速手段。注意：单路 TTFT 样本少且本身波动大（此前 59~103s），35.2s 仅供参考，以并发分位数为准。
- 备注：压测首日因方舟账号欠费（`AccountOverdueError` 403）导致 intent/rerank/report 全部降级，充值后恢复，压测数据为充值后所测。

**intent/rerank 修复（2026-09-08）**：
- 纠偏：上文「配置缺陷」判断（超时阈值太短）不完整。真正根因 = **AI SDK 4.0.50 对火山方舟推理模型的 reasoning output 类型校验 bug**：deepseek-v4-pro 的 responses 返回含 `"type":"reasoning"` 元素，AI SDK 响应 schema 不识别 → 非流式 `generateText`/`generateObject` 抛 `Invalid JSON response`（来自 `provider-utils/response-handler.ts` 的 `createJsonResponseHandler`）。
- 关键差异：非流式 `doGenerate` 踩该 bug；流式 `streamText` 有容错 → 报告生成一直正常。
- 修复：`IntentService`（原 `generateObject`）、`RerankService`（原 `generateText`）均改为 **`streamText`（流式）+ 手动提取 JSON + zod 校验**；新增 `extractJson` 纯函数（围栏 → 整段 parse → 首尾花括号截取三级容错）。
- 验证：新问题实测 `llm_calls_total{scene="intent",status="ok"}`、`{scene="rerank",status="ok"}` 恢复；intent 正确回填 countries/indicators/yearFrom/yearTo/routeHints；rerank 不再超时。单测 570 项通过（唯一失败为联网 WDI 验收项偶发超时，重跑通过）。
- 并发压测基线（恢复后，并发 10/20 路、timeout=180s）：成功率 100%、断连 0、总耗时 **P50=56.3s / P95=89.3s / P99=91.9s**（对比降级时 35.4s / 55.5s / 63.9s，上涨约 +60%）。链路稳定无回归，时间代价主要来自 rerank（推理模型 listwise 排序，约 30s 且不稳定，缩短候选实测无效）。
- 待办：embedding 模型名直调 404（方舟 embedding 需控制台「开通管理→向量模型」开通或创建推理接入点拿 `ep-xxx`），待用户侧处理后配 `EMBED_MODEL`。

**登录防刷**（提交 2bc35bc）：

- 新增错误码 `LOGIN_LOCKED=1010`；单测 `login-guard.spec` 3 项

**敏感词拦截（D8）复核**：`checkSensitiveWord` 仍在智搜 `setHeader`（首包回写）之前执行，拦截时序无回归，无需改动。

**渗透自测脚本**（`backend/scripts/security-audit.mjs`，零依赖）：未授权路由扫描、租户越权矩阵（直读+列表）、SQL/脚本注入探测、支付回调重放（下单→mock-pay→重放→订阅到期时间比对）、X-Forwarded-For 限流绕过；`npm run bench:audit` 运行。

**实测发现并修复两个安全缺陷**（2026-09-02）：
1. **租户列表泄漏（高危）**：`tenant-filter.ts` 的 `applyTenantFilter` 原来只在 `where !== undefined` 时注入 `tenantId`，`findMany` 不带 where（如知识库列表）退化为全表查询，B 租户可在列表中看到 A 租户的 PRIVATE 库（直读详情正常 404）。修复：WHERE 类操作一律注入（where 缺省时创建 `{ tenantId }`）；`tenant-filter.spec` 补 2 项用例
