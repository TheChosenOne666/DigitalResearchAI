## 一、选型背景与定位

| 项 | 结论 |
| --- | --- |
| 产品定位 | 对外商业化 SaaS 多租户平台 |
| 核心形态 | 一站式数据智能搜索（AI 智搜）+ 知识库 RAG + 数据分析工作台 + 报告生成 |
| 负载特征 | I/O 密集为主（三路并行检索、网页抓取、SSE 流式推送、LLM API 调用），CPU 密集较少（Excel 解析、数据标准化） |
| 团队模式 | 全栈 TypeScript 一人多端开发 |

**核心设计哲学（来自产品决策）**：

```
用户提问 → 意图分类（结构化条件抽取）
  ↓ 三路并行路由
  ├─ 本地：租户知识库（向量+全文混合检索）
  ├─ 联网：实时类问题 → AnySearch 聚合搜索直连（返回结构化正文，无需自抓）
  └─ 垂直 API：专业领域结构化数据（WDI/统计局类）
  ↓
整合：RRF 融合 → 打分排序 → Rerank 重排 → 过滤
  ↓
Agent 拿到干净的高质量上下文，直接推理生成报告
```

**Pipeline-First**：数据获取、清洗、融合是确定性工程（可单测、可控质量），Agent 只做综合推理不做数据脏活。这是整个平台的核心竞争力，也是所有技术选型的主轴。

## 三、关键技术决策记录

### 3.1 后端语言：Node.js 全栈（已决策）

**决策**：放弃 Java（SpringBoot3+Java21），采用 Node.js 全栈。

**理由**：
- 平台负载以 I/O 密集为主：三路并行检索、网页抓取、SSE 流式推送、LLM API 长连接，均为 Node 事件循环强项
- Vercel AI SDK / 流式生态一线支持，智搜链路 DX 最舒服
- 前后端 TypeScript 统一，DTO 类型共享，全栈一人开发效率最高

**代价（已知情）**：
- 放弃既有 SpringBoot3 模板积累与 Java 求职对齐
- 多租户计费、支付对账类事务场景需自行保证严谨性（Prisma 交互式事务 + 唯一约束兜底）
- CPU 密集任务（大数据文件解析）需 worker_threads / 队列异步化绕路

**备选方案（已否决）**：
- 纯 Java：技术可行（LangChain4j + WebFlux），但 AI 生态 DX 略逊，且用户主动倾向 Node
- Java+Node 混合：Java 管 SaaS 业务底座、Node 做 AI 编排，职责清晰但两套运维成本，小团队不划算

### 3.2 大模型接入：国内 API（已决策）

- 主力火山方舟 DeepSeek-V4-Pro-GA（260813，方舟托管稳定版），备选方舟豆包 Seed；统一 OpenAI 兼容协议 Provider 抽象，配置切换 model 即可
- Embedding：M3 知识库阶段选型（M2 不涉及）；Rerank：方舟 rerank 绑定 VikingDB 无独立 API，M2 开发期降级为 RRF 截断不精排，后续再选独立 rerank 方案
- 不自部署开源模型（无 GPU 资源诉求，成本不划算）

### 3.3 数据供给：三路并行（已决策）

按用户提问意图分类路由：

| 路 | 触发场景 | 数据质量保障方式 |
| --- | --- | --- |
| 本地 | 用户上传/入库的私有数据 | 混合检索（向量+全文）+ 库级向量化配置 |
| 联网 | 偏实时的问题 | AnySearch 聚合搜索直连，返回结构化正文（title/url/snippet/content），无需自建抓取与清洗 |
| 垂直 API | 专业领域结构化数据 | 指标/字典体系做 API 到标准字段的映射（起步：世界银行 WDI） |

三路结果经 RRF 融合、打分排序、Rerank 重排、过滤后交给 Agent 直接推理。

### 3.4 检索融合算法

- **RRF（Reciprocal Rank Fusion）**：`score(d) = Σ 1/(k + rank_i(d))`，k=60；多路命中加权
- **重排**：开发期降级——RRF 分数直接截断不精排（方舟 rerank 绑 VikingDB 无独立 API；后续再选独立 rerank 方案）
- **过滤**：SimHash 去重 + 相似度阈值截断 + TopK
