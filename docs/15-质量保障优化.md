## 一、环境变量启动校验（已完成，2026-09-03）

**问题**：ConfigService 读配置无校验，配置错（Redis 地址错、`RATE_SSE_MAX_CONCURRENT` 非数字）潜伏到运行期才在某个请求路径上炸。

**方案**：zod schema（`backend/src/common/config/env.schema.ts`）+ `ConfigModule.forRoot({ validate })`（app.module.ts）。复用现有 zod 依赖，未新增包；不动现有 `config.get(key, default)` 读取点。

**校验规则**：
- 必填：`DATABASE_URL` / `REDIS_URL` / `QDRANT_URL`（URL 格式校验），缺失启动即失败并打印具体字段
- 可选带类型：`APP_PORT`(1-65535)、`RATE_*`（正数/正整数）、`LOG_LEVEL`（枚举）、布尔开关（仅 true/false）、`BACKUP_*`、`SENTRY_*`、`OTEL_*`
- 新增环境变量时需同步维护 schema 与 `.env.example`

**验证**：单测 `env.schema.spec.ts` 9 项（最小配置通过 / 缺各项必填报错 / 非法数字 / 越界端口 / 非法布尔 / 非法枚举 / 合法 coerce）；全量后端回归 59 文件 498 测试通过；eslint 0 error。

## 三、检索优化三项（已完成，2026-09-06）

> 背景：针对智搜链路（联网/本地/混合）的系统分析发现三个硬伤：全文路 ILIKE 全表扫、无搜索缓存、无 rerank 精排层。

### 优化 A：pg_trgm 全文索引（消除全表扫描）

**问题**：`kb_chunks` 全文路 `ILIKE '%词%'` 前缀通配走不了 B-tree，每次检索全表扫；且原 SQL 用 `unnest` 变量 pattern，即使加了索引也永远不可用（计划期无法从变量提取 trigram）。

**改动**：
- 迁移 `20260906100000_search_trgm_index`：`CREATE EXTENSION pg_trgm` + `content gin_trgm_ops` GIN 索引（Prisma 迁移包事务执行，CONCURRENTLY 不可用；当前规模锁表瞬时）
- `kb.store.service.ts searchChunksFulltext` 重写：unnest 相关子查询 → `Prisma.join` 组合的 OR 展开参数化 ILIKE（matchedTerms 由 CASE 求和计算，排序语义不变）

**验证**：`SET enable_seqscan=off` 下 EXPLAIN 显示 `Bitmap Index Scan on idx_kb_chunks_content_trgm`（Index Cond: content ~~*）；实测搜索 3 来源正常返回。

### 优化 B：搜索结果 Redis 短缓存

**改动**：新增 `SearchCacheService`（`search-cache.service.ts`）+ controller 接入：
- key = `search:cache:{tenantId}:{mode}:{question哈希}:{conditions哈希}`，TTL 600s（Redis `SET ... EX`）
- 只缓存检索融合结果（FusionResult），报告生成照常流式（体验保留）；配额计费不受影响（拦截在缓存判断之前）
- Redis 不可用/结构异常 → 静默降级透传（不缓存不报错）

**验证**：单测 5 项（命中/条件隔离/租户隔离/降级/脏缓存）；实测同题第二次搜索 Redis MONITOR 仅 GET 无 SET（命中证明），缓存键 TTL=600s。

### 优化 C：LLM listwise 精排

**改动**：新增 `RerankService`（`fusion/rerank.service.ts`）+ controller 在融合后接入：
- 融合 TopK（cited+referenced）→ LLM listwise 排序（输出 JSON 编号数组）→ 按原引用级门槛重新切分 cited/referenced
- 精排后顺序随缓存一并保存（缓存命中不再重复精排）
- 未启用（无 ARK_API_KEY）/ 候选不足 2 条 → 跳过；超时 3s / 解析失败 → 回退 RRF 原序（降级链与全项目一致）
- 指标：`llm_calls_total{scene="rerank", status=ok|error|skipped}`（metrics.service llmCall 签名扩展）

**验证**：单测 10 项（解析纯函数/提示词构造/跳过/重排含遗漏补尾/解析失败回退/调用异常回退）+ controller 编排 2 项（精排重切分随缓存保存/失败回退原序）；实测无 Key 环境 pipeline 正常完成（降级路径）。

### 汇总

- 全量后端回归 **61 文件 516 测试通过**；eslint 0 error；改动文件 lint 仅既有风格 warning
- 未新增 npm 依赖（复用 zod/ioredis/ai sdk）；未改 SSE 协议（前端零改动）
- 已知取舍：知识库新入库文档 10 分钟缓存窗口内搜不到（可加入库清缓存钩子，暂不做）

## 四、SSE 心跳（已完成，2026-09-06）

**问题**：`search/stream` 与 `workspace/analyze` 两个 SSE 端点在生成阶段 LLM 可能 30s+ 无输出，无心跳帧会被网关/反向代理 idle timeout 掐断半开连接。

**方案**：SSE 标准注释帧 `: ping\n\n`（标准客户端自动忽略，前端两个流解析器本就跳过 `:` 开头行，前端零改动）。

**改动**：
- 新增 `common/sse/sse-heartbeat.util.ts`：`startSseHeartbeat(res, ac, intervalMs)` 返回幂等停止函数；write 异常或 res error 事件时停止心跳并 `ac.abort()` 尽早释放业务链路
- 两个 controller 各接入一处，finally 中停止
- `env.schema` 新增可选 `SSE_HEARTBEAT_MS`（默认 15000，≤0 禁用）

**验证**：单测 `sse-heartbeat.spec.ts`（正常写帧/间隔可配/≤0 禁用/停止清理/写失败触发 abort）；全量回归通过。

## 五、BullMQ 可靠性：死信 + 告警 + 幂等（已完成，2026-09-06）

**问题**：3 次重试耗尽后 job 留在 failed set，无监听无告警无清理；`add('learn')` 无 jobId，重复点击 relearn / 审核重触发会重复入队，concurrency=2 下同一文档可能并发学习（deleteChunks→writeChunks 竞态）；两个生产者各自 new Queue、参数散落。

**方案**（不改协议、不加依赖）：
- 新增 `kb/queue/learn-queue.ts` 队列工厂：`submitLearn()` 统一入队，`jobId = learn:{documentId}`（重试等待期内重复提交被 BullMQ 去重）+ `removeOnComplete: true`（完成后释放 jobId，relearn 可重跑）；两个生产者（kb.service / kb-admin 侧）统一改走工厂
- processor 挂 `failed` 事件（最终失败）：error 日志 + `queue_jobs_failed_total` 指标 + payload 连同失败原因转投死信队列 `chunk-embed-dlq`（无 worker，仅留存 7 天供排查，每小时清理过期任务）
- metrics 新增 `queue_jobs_failed_total`

**验证**：单测 `learn-queue.spec.ts`（jobId 去重参数/DLQ 转投/removeOn 配置）；全量回归通过。
