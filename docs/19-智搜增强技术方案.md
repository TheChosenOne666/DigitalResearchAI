## 批 1 实施偏差记录（2026-09-10）

| 项 | 原设计 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 引文标注 | 「上标 `[N]`」 | **小字号 + 主题蓝 + 方括号**（非真上标） | pdfkit 0.20 运行时不支持 `superscript`（源码无该选项），Word 侧仍为真上标 |
| 加粗 | 保留加粗 | 正文同字重（内容不丢） | 未注册独立粗体字体，避免为视觉加粗引入额外字体资源 |
| TTC 字体选择 | `family` 名 | **PostScript 名**（如 `MicrosoftYaHei`） | pdfkit 第三参数透传 fontkit，实为 PostScript 名；传 family 展示名会报错 |
| 字体加载失败检测 | `registerFont` 抛错即降级 | 注册后**立即 `font()` 触发加载**再降级 | pdfkit 注册是惰性的，不立即选用则错误不会暴露 |

字体策略：`PDF_FONT_PATH` 优先，未配置按平台兜底（Windows 微软雅黑→黑体→宋体；Linux 思源黑体→文泉驿；macOS 苹方）；全部失败抛业务异常（不静默输出乱码）。**生产容器需安装中文字体**（记入 M7.5 docker 化清单）。

## 批 3 实施记录（2026-09-10）

数据设计取技术方案 3.3 的**方案 A**（新增表），实现中修正两处细节：

| 项 | 设计 | 实际实现 | 说明 |
| --- | --- | --- | --- |
| `status` 字段 | 表含 `status`（parsed/failed） | **删除该字段** | 解析失败的文件不落库（原因随响应返回），字段恒为 parsed，属冗余 |
| multer 大小限制 | `limits.fileSize = 20MB` | **放宽到 2 倍（40MB）**，精确校验在 service | multer 的 fileSize 是**请求级硬限制**，超限整体 413，与「单文件超限只标记该文件失败」的需求冲突；40MB 仅作内存保护线 |
| 文件名编码 | 未涉及 | **`defParamCharset: 'utf8'`** | multer 默认按 latin1 解码 multipart filename，中文名变乱码（`A资料.txt` → `Aèµæ.txt`），真实浏览器上传同样中招，必须显式指定 |
| 类型体系 | `SourceType` 加 `upload` | 新增 `ConnectorSourceType = Exclude<SourceType,'upload'>` | upload 不经过连接器检索，用独立类型避免 `CONNECTOR_TIMEOUT_MS` 等映射被迫带上无用键 |
| 并入方式 | 前置并入来源 | 同设计；在 `trackSearchTerm` **之后**并入 | 避免上传资料影响「搜索词/无结果词」的检索维度统计口径 |

清理策略：`expiresAt`（30 分钟，与检索快照一致）+ **懒删除**（每次上传顺手清该用户过期记录），不引入定时任务。

**文件名编码（口径说明，含一次误判的纠正）**：multer 默认 `defParamCharset: 'latin1'` 会让 multipart 的中文文件名乱码，本批在 `search/uploads` 用 **`defParamCharset: 'utf8'` 从源头修复**。
另两条既有上传链路经核查**不受影响、无需改动**：
- 知识库上传（`kb.controller.ts`）已有 `decodeUploadFilename()`（`Buffer.from(name,'latin1').toString('utf8')`）做补偿，中文名本来正常；
- 工作台上传（`workspace.controller.ts`）只用文件名推断扩展名（ASCII），**不落库文件名**（`workspace.upload(mime, buffer)` 不接收名字）。

> ⚠️ **纠正**：曾误判这两条链路为「同样会乱码」并统一加 `defParamCharset: 'utf8'`，实测反而因**二次解码**把 kb 的中文名弄坏（`中文研究报告2024.txt` → 控制字符乱码），已回滚。两条链路修法不同（源头修复 vs 补偿函数），**后续若要统一，必须同时删掉 `decodeUploadFilename` 的调用**并回归其单测。

## 批 4 实施记录（2026-09-10）

按设计落地（**断点续跑取方案 A：章节分段生成**），实现中修正/简化了四处：

| 项 | 设计 | 实际实现 | 说明 |
| --- | --- | --- | --- |
| 断点机制 | 逐章生成 + `search_report_segments` 落库 | 同设计；报告新增 `status`(DRAFT/COMPLETE) 与 `segmentIdx` | 中断后从 `segmentIdx` 续跑，**天然无重复段落**（实测 3 章各出现 1 次） |
| 任务并发上限 + 排队 | `SEARCH_MAX_ACTIVE_TASKS` + QUEUED 排队自动推进 | **不做**，复用既有 SSE 槽位限流（M7.2，超限 429） | 真排队需把检索/生成改造成后台作业（BullMQ），与「SSE 直连」模型冲突；状态机中去掉 QUEUED |
| 跨请求中止 | （未定） | 用**任务状态本身**做信号：`abort` 接口置 ABORTED，生成流程在**章节边界**重读状态后停止 | 零新增依赖（不引入 Redis 标记），分段生成天然提供检查点 |
| 重试 | `POST /tasks/:id/retry` | **不提供**：检索失败时试额已回滚，前端用原问题重新发起检索即可 | 净效果等价于「不重复扣费」，少一个接口 |
| 任务列表 question | 表内冗余 或 关联查 | 批量查会话组装（`IN` 一次查询） | 与 M6.1 `import_tasks` 的既有处理一致，避免为展示字段加冗余列 |
| 章节进度可见性 | — | 新增 SSE `section_done` 事件（`{idx, heading, doneCount, total}`） | 前端可显示「已完成 x/3 章」，也是断点位置对外的可见信号，联调脚本据此精确模拟中断 |

**修复的实现缺陷（联调暴露）**：首次实现中，章节边界中断后流程仍继续执行 `completeReport`，会把**不完整报告标成 COMPLETE** 并进入历史/可导出。已改为「`doneCount < 总章节数` → 置 ABORTED、保留草稿、推 error 事件、不落 COMPLETE」，并补单测作为回归护栏。

**已知取舍**：草稿报告（DRAFT）不出现在历史/报告详情（列表与详情查询均按 `status='COMPLETE'` 过滤）；任务记录删除不连带删除报告；僵尸任务在**服务启动时**收敛（不引入定时任务）。

**新增**
- `backend/test/search/local-first.spec.ts`

### 2.3 判定规则

```
本地结果 hits：
  hits.length >= KB_FIRST_MIN_HITS(默认 3) 且 max(score) >= KB_FIRST_MIN_SCORE(默认 0.5)
    → 短路：不调用 web/vertical 连接器

```

- 本地路为空 / 本地路失败（超时）→ 视为不足，正常兜底（不报错）

### 3.2 接口

```
POST /api/v1/search/uploads        multipart/form-data，字段 files（多文件）
  → 200 { files: [{ id, name, size, mimeType, status: 'parsed'|'failed', error? }] }
    校验：格式白名单 xlsx/xls/csv/docx/doc/pdf/txt/md；单文件 ≤ 20MB；单次 ≤ 5 个
    解析失败的文件返回 status='failed' + error，不阻断其余文件

POST /api/v1/search/stream         body 增可选字段 uploadIds: string[]
  → 检索完成后，上传资料作为 sourceType='upload' 的来源**置顶**进入选数据态，
    与检索来源统一连续编号（1..N，上传资料占 1..k）
```

### 3.3 数据设计（二选一，推荐方案 A）

- **方案 A（推荐）**：新增表 `search_uploads`（id/tenantId/userId/name/mimeType/size/contentMd/status/createdAt/expiresAt），检索时按 uploadIds 取内容并注入快照。可复用、可审计，清理策略有落点。
- **方案 B**：不建表，解析结果直接作为请求内联内容随 `stream` 传入（前端持有）。零表变更，但内容经前端往返、无法服务端清理、长文档受请求体限制。

清理：`expiresAt`（默认 30 分钟，与检索快照一致），由定期任务或懒删除处理；任务删除时一并清理。

### 3.4 计费与边界

- 上传不单独计费（同一次检索会话扣 1 次）
- 解析文本长度上限（建议单文件 ≤ 5 万字符，超出截断并标注），防止撑爆生成上下文
- 不自动入知识库（用户明确选择「作为本次来源」）

### 3.5 单测

格式白名单 / 大小上限 / 数量上限 / 解析失败不阻断 / 上传资料并入来源且编号连续 / 仅上传资料也能生成 / 过期清理 / 跨用户不可访问他人 uploadId。

| type | varchar(16) | `retrieval` / `generate` |
| status | varchar(24) | `QUEUED`/`RETRIEVING`/`PENDING_SELECT`/`GENERATING`/`DONE`/`RETRIEVAL_FAILED`/`GENERATE_FAILED`/`ABORTED` |
| progress | int | 0-100（生成阶段按已完成章节数折算） |
| errorMsg | varchar(512) | 失败原因 |
| createdAt / updatedAt / finishedAt | timestamp | 时间戳 |

状态机：`QUEUED → RETRIEVING → PENDING_SELECT → GENERATING → DONE`；任一步失败 → `*_FAILED`；中止 → `ABORTED`。`*_FAILED`/`ABORTED` 均可重试或续跑。

**`search_reports` 扩展**
- `status`：`DRAFT`（生成中/中断，仅内部可见）/ `COMPLETE`（完成，参与展示与导出）
- `segmentIdx`：已完成章节序号（用于续跑定位）
- 新增 `search_report_segments` 表（reportId/segmentIdx/contentMd/createdAt）存储各章节已生成内容 —— 断点的真实载体

### 4.3 接口

```
GET    /api/v1/search/tasks?status=active|done|failed&page=&pageSize=
       → { list: [{ id, sessionId, type, status, progress, question, errorMsg, createdAt, updatedAt }], total }
POST   /api/v1/search/tasks/:id/abort      → 中止（进行中）
POST   /api/v1/search/tasks/:id/retry      → 检索失败重试（重新检索）
POST   /api/v1/search/tasks/:id/resume     → 生成中断续跑（从 segmentIdx+1 继续，SSE）
DELETE /api/v1/search/tasks/:id            → 删除任务记录（不删报告）
```

- 全部按租户 + 用户隔离；越权一律 404
- 生成入口 `POST /search/stream/generate` 内部创建/推进 generate 任务
- 并发上限：`SEARCH_MAX_ACTIVE_TASKS`（默认 2），超出创建 `QUEUED`；前序任务结束（DONE/FAILED/ABORTED）后由创建/结束时统一触发排队推进

### 4.4 断点续跑实现（**待确认架构决策**）

**方案 A：章节分段生成（推荐）**
报告模板固定三章（核心结论 / 关键数据 / 分析解读，见 `generate.service.ts` 的 `GENERATE_SYSTEM`）。改为**逐章生成、逐章落库**（`search_report_segments`），每章完成即推进 `segmentIdx`。
- 中断后从 `segmentIdx + 1` 继续，天然**无重复段落、无拼接断裂**（满足需求 1 验收标准）
- 每章一次 LLM 调用（带前序章节摘要作上下文，保证连贯），总耗时略增，但每章更短、首屏更快
- 续跑不重复检索、不重复计费（计费仍在检索段）

**方案 B：单次流式 + 定期快照 + LLM 续写**
- 生成过程中每 N 秒落一次已生成文本，中断后把已有文本作为前文让 LLM 续写
- 缺点：**重复/断裂风险高**（LLM 倾向重述前文），token 重复计费，难以保证验收标准「无重复段落」

**结论：采用方案 A**。如需保留一次性生成的整体连贯性，可折中为「段落级落库 + 章节边界续写」。

### 4.5 风险与回归点

- **僵尸态**：服务重启后在途任务（`RETRIEVING`/`GENERATING`）不会自愈 → 启动时把超时未更新的在途任务置为 `*_FAILED`（可续跑），避免"永远卡在进行中"
- **并发竞争**：同一任务的重复点击与并发推进需幂等（状态前置校验 + 乐观更新）
- **计费一致性**：重试/续跑不得重复扣费，需在任务上记录是否已扣费
- **SSE 协议**：续跑为独立 SSE 端点，不复用 `stream/generate`，避免与两段式语义缠斗
- **前端回归**：任务面板不得影响现有「检索→选择→生成」主流程；历史记录入口行为不变

## 七、续跑窗口落地（2026-09-10 晚，追加修订）

### 7.1 背景：一个只在一处生效的窗口

复核批 4 时发现 TTL 三处**并不一致**（初版记录曾笼统写作"窗口从未生效"，**此处更正**）：

| 路径 | 改前行为 |
|---|---|
| 快照恢复接口 `GET /search/retrievals/:sessionId` | ✅ 计算并返回 `expiresInSeconds`（≤0 前端提示重新检索） |
| **生成入口** `generateFromSelection` | ✅ **已强制校验**：`expiresInSeconds <= 0` → `BizException(3001)`「检索结果已过期（超过 30 分钟），请重新勾选并点击开始分析」 |
| **续跑** `resumeTask` | ❌ **只校验快照是否存在（`if (!snapshot)`），不校验 TTL** |
| 过期快照的物理清理 | ❌ 全项目无 `@Cron`/`ScheduleModule`，`search_retrieval` 行永不删除（行内含来源正文 JSON，会持续堆积） |

即：**窗口在生成路径早已生效，漏的是续跑路径；过期数据则完全没有回收**。本次把两者补齐并统一。

### 7.2 改动

| 位置 | 改动 |
|---|---|
| `search/search.constants.ts` | `RETRIEVAL_TTL_SECONDS` 不再本地定义，改为从 `@app/shared` **转出**（前后端共用一份）；生成路径的提示文案一并改为按常量计算（原先硬编码「30 分钟」） |
| `search.controller.ts` · `resumeTask` | 增加过期判定：`!snapshot \|\| 剩余 ≤ 0` → 抛 `BizException(3001)`，提示「检索结果已过期（超过 30 分钟），请重新勾选并点击开始分析」，并打 warn 日志 |

### 7.3 设计要点

- **校验位置在 SSE 响应头之前**：`resumeTask` 的过期判定位于 `acquireSseSlot` / `flushHeaders` 之前，因此客户端收到的是**真实的 HTTP 400**（而非 SSE `error` 事件），也不占用 SSE 槽位。这是刻意选择——前置校验能给出正确的 HTTP 语义与状态码。
- **过期不改变任务状态**：仍为「生成中断 / 已中止」，断点内容保留，仅可用动作变化（前端据此切换按钮），避免为一个临时窗口引入新状态。
- **过期快照清理走懒删除**（沿用 `search_uploads` 的既有口径）：每次新检索顺手回收本租户过期行，**不引入调度器**。代价是「长期不检索的租户其过期行会滞留」——与上传资料清理是同一取舍；如需彻底回收，再引入 `@nestjs/schedule` 或独立清理任务。
- **该表的租户隔离依赖会话链**：`search_retrieval` 无 `tenantId` 列且未登记 `TENANT_MODELS`，因此 `forTenant.searchRetrieval.*` 实际**不注入租户过滤**（详见 §八 遗留项）。本次清理显式用 `session: { tenantId }` 关系过滤，不依赖隐式注入。

### 10.6 过期会话仍可回到首页智搜（2026-09-13）

**问题（含一次方向纠正）**：用户点历史记录里的「待选择」会话后，若快照已过期，页面**只弹一条提示就停住**，会话内容完全不渲染——用户既回不到那个记录，也不知道发生了什么。

## 十一、租户隔离缺陷修复（2026-09-10）

### 9.1 缺陷（可复现的越权读取）

`SearchRetrieval` / `SearchReport` / `SearchSource` / `SearchReportSegment` 四张表**均无 `tenant_id` 列**，隔离仅依赖「所属会话链 + sessionId 为不可枚举 cuid」：

- `SearchRetrieval` **未登记** `TENANT_MODELS` → `forTenant.searchRetrieval.*` 不做任何租户过滤；
- `SearchReport` / `SearchSource` **已登记却无该列** → 一旦直接 `forTenant.searchReport.*` 会因未知参数报错（哑弹）。

后果最直接的是 `GET /search/retrievals/:sessionId`：只凭 sessionId 即返回快照。**实测复现**（两个 dev 账号分属不同租户）：B 租户请求 A 租户的 sessionId → `HTTP 200`，返回 A 的检索问题原文（含刻意埋入的标记串）与 **10 条来源全部正文**。

生成路径本身不受影响（`createDraftReport` 前有会话归属校验，跨租户会被 404 拒绝），故泄漏面为**只读**。

### 9.2 修复

| 步骤 | 内容 |
|---|---|
| schema | 四张表各增 `tenantId String @map("tenant_id") @db.VarChar(32)` + `@@index([tenantId])` |
| 迁移 | `20260910122652_tenant_id_for_search_child_tables`：因历史数据非空（71 报告 / 513 来源 / 21 快照 / 20 章节），采用**三步法**——先加可空列 → 从会话链回填（章节/来源经 `report_id` 取报告的租户）→ 再 `SET NOT NULL`；**不做孤儿兜底删除**，若回填后仍有 NULL 则迁移直接失败（不静默丢数据） |
| 回填校验 | 迁移后逐表核对：全部行已填充，且与所属会话/报告的 `tenant_id` **0 行不一致** |
| 隔离登记 | `TENANT_MODELS` 增补 `SearchRetrieval`、`SearchReportSegment`（`SearchReport`/`SearchSource` 原已登记） |
| 写入路径 | 租户扩展**只注入顶层参数，不处理嵌套 create**；且多处写入走系统 client。故显式补 `tenantId`：`saveReport`（报告 + 来源嵌套 create）、`createDraftReport`（嵌套 create）、`saveSegment`（章节 upsert create）、`completeReport`（来源嵌套 create）、`saveRetrieval`（upsert create）、`purgeExpiredRetrievals`（deleteMany 的 where，破坏性操作不依赖隐式注入） |
| 注释修正 | `getRetrieval` 处「跨租户视为不存在」的表述在修复后才成立；`purgeExpiredRetrievals` 原注释中「无 tenantId 列、故用关系过滤」的描述一并更正 |

### 9.3 验证

- **越权回归（修复前后对照）**：同一条复现路径，修复前 `HTTP 200` + 泄露问题与 10 条来源 → 修复后 `HTTP 404`、返回体无任何业务数据；跨租户生成请求亦由「200 + SSE error」变为**真实 404**（校验位于 `flushHeaders()` 之前）。
- **正常链路回归**：完整生成（草稿/章节/来源三处嵌套写）+ 断点续跑均正常；直查库确认报告、3 章节、10 来源的 `tenant_id` 全部写入，**全库四表 `tenant_id` 为空行数均为 0**。
- **单测**：新增「智搜从表已登记且读/删路径均注入」「**不变量：清单内每个模型在 schema 中都声明了 tenantId**」（直接解析 `schema.prisma`，防同类错误再犯）；store 侧新增 `saveRetrieval` create 带 tenantId、清理条件改用显式 tenantId；`saveReport` 用例补租户上下文与 tenantId 断言。后端全量 **68 文件 / 663 用例全绿**，`tsc --noEmit`（src 零错误）。
